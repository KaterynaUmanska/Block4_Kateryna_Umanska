# NodeJS

## Предметна область

PurchaseRecord (запис про закупівлю) - основна сутність, яка представляє окрему позицію (рядок) виробничого замовлення на закупівлю матеріалів. Кожен запис PurchaseRecord відповідає одному конкретному матеріалу та містить його необхідну кількість. Кожна позиція також має ідентифікатор виробничого замовлення orderId, до якого вона належить.

Material (матеріал) - другорядна сутність, яка містить інформацію про матеріали, що використовуються у виробничому процесі та можуть бути включені до позицій закупівлі. Кожен матеріал має унікальну назву та визначену одиницю вимірювання.

ChangesHistory (історія змін) - сутність, яка зберігає інформацію про зміни окремих записів закупівлі (PurchaseRecord) із Block2. Кожен запис історії містить ідентифікатор зміненого запису, назву зміненого поля, його попереднє та нове значення, а також час зміни.

Атрибути сутності:

- id (ObjectId) - унікальний ідентифікатор запису історії змін.
- recordId (Long) - ідентифікатор запису PurchaseRecord із Block2, якого стосується зміна.
- changedAt (Date) - дата й час зміни.
- fieldName (String) - назва поля, яке було змінено. Приймає значення: orderId, material, quantity.
- oldValue (String) - попереднє значення поля.
- newValue (String) - нове значення поля.

Поле changedAt заповнюється поточним часом автоматично, якщо його значення не передано під час створення запису.


Основним зв'язком у проєкті є зв'язок Many-to-One між PurchaseRecord та Material. Кожен PurchaseRecord посилається рівно на один Material, а один Material може використовуватися у багатьох PurchaseRecord. 

Також реалізовано зв'язок  Many-to-One між ChangesHistory та PurchaseRecord. Кожен запис ChangesHistory належить одному запису PurchaseRecord, а один PurchaseRecord може мати багато записів історії змін.

PurchaseRecord зберігається в PostgreSQL у Block2, а ChangesHistory - у MongoDB у Block4.

Зв'язок реалізується через поле recordId. Це логічний зв'язок між сервісами, а не зовнішній ключ у MongoDB.

Під час створення запису історії Block4 перевіряє існування відповідного PurchaseRecord через REST API Block2.

## REST API

### Створення запису історії змін

`POST /api/changes-history`

Створює запис історії змін після перевірки переданих даних та існування пов'язаного PurchaseRecord у Block2.

Приклад запиту:

```json
{
  "recordId": 101,
  "fieldName": "quantity",
  "oldValue": "10",
  "newValue": "15"
}
```

Поле changedAt можна передати явно. Якщо його не передано, використовується поточний час.

### Отримання історії змін

`GET /api/changes-history?recordId={id}&size={size}&from={from}`

Повертає записи історії змін для вказаного recordId, відсортовані за часом зміни від найновіших до найстаріших.

Параметри:
- recordId - ідентифікатор запису PurchaseRecord.
- size - максимальна кількість записів у відповіді.
- from - кількість записів, які потрібно пропустити перед поверненням результатів.

### Підрахунок записів історії

`POST /api/changes-history/_counts`

Повертає кількість записів історії змін для кожного переданого recordId.

Приклад запиту:

```json
{
  "recordIds": [101, 414, 999]
}
```

Приклад відповіді:

```json
{
  "101": 1,
  "414": 5,
  "999": 0
}
```

Для ідентифікаторів, які не мають записів історії, повертається 0.

Підрахунок виконується за допомогою агрегаційного запиту MongoDB. Використовуються операції групування та підрахунку, тому немає необхідності завантажувати всі документи історії в пам'ять застосунку.

## База даних

Додаток використовує MongoDB Atlas - хмарний сервіс для зберігання та керування документною базою даних MongoDB

Колекція MongoDB changes_history.

Основні поля:
- recordId - ідентифікатор пов'язаного запису Block2;
- changedAt - час зміни;
- fieldName - змінене поле;
- oldValue - попереднє значення;
- newValue - нове значення.

Для прискорення пошуку за записом та отримання історії в хронологічному порядку використовується складений індекс { recordId: 1, changedAt: -1 }.

## Взаємодія з Block2

Block2 - окремий сервіс на Java Spring Boot, який зберігає дані PurchaseRecord і Material у PostgreSQL.

Block4 не дублює ці дані у власній базі. Для перевірки існування PurchaseRecord він використовує REST API Block2, а в MongoDB зберігає лише історію змін і посилання на відповідний запис через recordId.


## Налаштування

Для роботи проєкту необхідно мати:
- Node.js
- npm
- Docker та Docker Compose
- Доступний сервіс Block2 для перевірки існування PurchaseRecord

## Змінні середовища

У репозиторії зберігається файл .env.example із прикладом конфігурації.

Для локального запуску створіть .env на основі .env.example і налаштуйте такі змінні:

- HOST - адреса, на якій запускається застосунок;
- PORT - порт застосунку, за замовчуванням 7777;
- MONGO_ADDRESS -  URI підключення до MongoDB;
- RECORD_SERVICE_URL - базова URL-адреса REST API сервісу Block2.

Приклад конфігурації для локального запуску:

HOST=localhost
PORT=7777
MONGO_ADDRESS=mongodb://localhost:27017/block4
RECORD_SERVICE_URL=http://localhost:8080

Якщо використовується MongoDB Atlas, у MONGO_ADDRESS потрібно вказати URI підключення до відповідного кластера.

Під час запуску через Docker Compose застосунок автоматично використовує MongoDB із сервісу mongo. У такому випадку MONGO_ADDRESS задається в docker-compose.yml і має значення mongodb://mongo:27017/block4.

Для підключення до Block2, запущеного на хост-машині, використовується адреса http://host.docker.internal:8080. Якщо сервіс працює на іншому порту, потрібно змінити RECORD_SERVICE_URL.

## Запуск застосунку

Перед запуском необхідно переконатися, що MongoDB доступна, а сервіс Block2 запущений і доступний за адресою, зазначеною в налаштуваннях.

Збірка: 

`npm run build`

Запуск:

`npm start`

Запуск через Docker Compose

`docker compose up --build`

Зупинка контейнерів:

`docker compose down`

## Тестування

Для перевірки роботи сервісу передбачені інтеграційні тести для всіх трьох endpoint:

- POST /api/changes-history - перевірка успішного створення запису історії змін, валідації вхідних даних і обробки ситуацій, коли пов'язаний PurchaseRecord не існує.

- GET /api/changes-history - перевірка отримання історії за recordId, сортування за часом у спадному порядку та пагінації за допомогою параметрів size і from.

- POST /api/changes-history/_counts - перевірка правильності підрахунку записів для переданих ідентифікаторів, повернення нульових значень для записів без історії та використання агрегації MongoDB.

Інтеграційні тести перевіряють взаємодію HTTP API з логікою сервісу та базою даних, а також коректність відповідей у типових і помилкових сценаріях.

Тести запускаються командою:

`npm test`

Для запуску тестів, які використовують Testcontainers, необхідно мати встановлений і запущений Docker.
